Pipeline de Veille Scientifique — Guide complet

Alexandria · Comment fonctionne la veille, étape par étape

Régénéré le 06/07/2026 — remplace une version antérieure décrivant un déclenchement manuel/Vercel avec polling en temps réel (~20s), abandonné pour timeout serverless.

Objectif : Chaque jour, Alexandria surveille automatiquement des dizaines de revues scientifiques pour en extraire les articles récents. Chaque article est ensuite comparé au corpus documentaire de l'application (les PDF déjà indexés) — et depuis juin 2026, également comparé aux seules publications du chercheur — pour obtenir un score de pertinence. Les articles les mieux notés reçoivent en plus une analyse IA individuelle, et le run se termine par une synthèse globale du jour.

Ce processus dure environ 6 à 8 minutes et se déclenche automatiquement chaque matin à 7h UTC (9h Paris) via GitHub Actions — pas de bouton, pas d'attente côté utilisateur : le chercheur consulte les résultats déjà calculés en visitant /bibliographie, à son rythme.

Déclenchement automatique

Instantané

Un workflow GitHub Actions se déclenche chaque matin à 7h UTC (9h Paris), sans aucune action du chercheur. Un déclenchement manuel (workflow_dispatch) reste possible pour les tests ou pour reprendre un run interrompu (run_id existant).

Chacun des 4 jobs qui suivent est une exécution indépendante d'un script Node.js sur un runner GitHub — pas un process unique qui reste ouvert pendant 8 minutes.

Pourquoi GitHub Actions et pas Vercel ?
Une ancienne version de ce pipeline tournait sur Vercel (fire-and-forget + waitUntil). Mais le plan Hobby limite les fonctions à 10s, et même en pratique waitUntil ne survit pas de façon fiable au-delà d'environ 150s. Résultat : des similarity_score = null en production. GitHub Actions n'a pas cette limite — voir docs/VEILLE_PIPELINE_REFACTOR.md.
↓Entrée : cron GitHub Actions ou déclenchement manuel
↑Sortie : run_id transmis via GITHUB_OUTPUT
1

Job 1 — Extraction (RSS + OpenAlex + CrossRef)

~1 min

scripts/veille/extract.ts fait tout en un seul job : lecture des 46 flux RSS actifs (5 en parallèle, fenêtre de 3 jours — pas 7, voir encadré), puis enrichissement OpenAlex par lot de 50 DOIs pour récupérer les résumés manquants (ACS, notamment, ne les met pas dans son RSS), résolution de DOI par titre pour les sources sans DOI (Elsevier), et fetch direct par ISSN pour les 2 sources MDPI qui n'ont pas de RSS fiable.

Un article n'est retenu que s'il est définitivement publié : OpenAlex doit confirmer is_final=true, sinon CrossRef prend le relais en vérification de secours (présence de volume/issue). Sans confirmation d'aucun des deux, l'article est rejeté (ASAP, preprint, correction).

Incohérence connue
Ce job utilise une fenêtre de 3 jours (LOOKBACK_DAYS). Un pipeline de secours plus ancien, conservé pour un déclenchement manuel via l'UI (lib/veille/pipeline.ts), est resté à 7 jours — deux fenêtres différentes coexistent selon le chemin emprunté.
↓Entrée : 46 sources RSS + 2 sources OpenAlex (ISSN)
↑Sortie : articles finalisés insérés dans veille_items
1b

Job 1b (optionnel) — Semantic Scholar

parallèle

Actif seulement si la variable repo ENABLE_SEMANTIC_SCHOLAR=true. Tourne en parallèle du Job 1, sans dépendre de lui. Utilise les articles auteur les plus représentatifs (ss_representative_papers, précalculés par compute-ss-representatives.ts après chaque ingestion --author) pour interroger l'API de recommandations Semantic Scholar : jusqu'à 100 papiers récents (60 jours) similaires au profil du chercheur.

Filtre abstract < 50 caractères + dédup DOI, puis insertion avec source_type='semantic_scholar'.

Pourquoi une source à part ?
RSS et OpenAlex couvrent les journaux surveillés explicitement. Semantic Scholar élargit la couverture à des articles similaires au profil du chercheur, publiés ailleurs — sans avoir à ajouter manuellement chaque nouvelle source.
↓Entrée : articles auteur représentatifs (centroïde embeddings)
↑Sortie : recommandations insérées dans veille_items
2

Job 2 — Scoring double (corpus + auteur)

~3 min

scripts/veille/score.ts charge tous les articles sans similarity_score (reprise automatique si le job avait été interrompu). Chaque résumé est découpé en chunks d'environ 150 mots (pas embeddé d'un seul bloc — un résumé entier de ~400 mots perd trop d'information pour le modèle all-MiniLM-L6-v2, entraîné sur des phrases courtes).

Chaque chunk est comparé en parallèle à deux référentiels : le corpus complet (match_chunks) et les seuls articles publiés par le chercheur (match_author_chunks). Le meilleur score de chaque référentiel devient respectivement similarity_score et author_score. Les passages ≥75% sont conservés comme corpus_refs (jusqu'à 5, avec extrait et page).

Pourquoi un double scoring ?
Un article peut ressembler au corpus général sans toucher précisément au sujet du chercheur. author_score — plus exigeant — sert de signal complémentaire, affiché en badge orange séparé sur les cards de veille.
↓Entrée : résumés + corpus (chunks non temporaires) + articles auteur
↑Sortie : similarity_score, author_score, corpus_refs
3

Job 3 — Analyse IA individuelle

~1,5 min

scripts/veille/recap-articles.ts charge jusqu'à 50 articles ≥75% (cap de sécurité — en pratique 5 à 10/jour dépassent ce seuil), mais n'envoie à GPT-4o-mini que le top 8 par score décroissant (MAX_ARTICLES=8 dans lib/veille/summarize.ts). Pour chacun : contribution scientifique, pertinence pour le chercheur, et lien précis avec le corpus (citant titres et pages).

Point souvent mal compris
Un article ≥75% n'a donc pas la garantie d'obtenir une analyse IA — seuls les 8 mieux classés du jour l'obtiennent. Au-delà de 8 articles ≥75% dans une même run, les suivants restent sans ai_analysis, même s'ils sont visibles sur /bibliographie.
↓Entrée : top 8 articles ≥75% + leurs corpus_refs
↑Sortie : ai_analysis par article traité
4

Job 4 — Synthèse globale & clôture

~30s

scripts/veille/recap-global.ts charge les articles ayant un ai_analysis et un similarity_score ≥ 80% — un seuil plus strict que celui de l'analyse individuelle. GPT-4o-mini produit 2 à 4 thèmes transversaux et une synthèse en vouvoiement, à partir des analyses déjà générées (pas des résumés bruts, pour limiter les tokens).

Le run est ensuite marqué completed — c'est ce job, et lui seul, qui clôture officiellement la run.

Seuil à deux vitesses
Un article à 76-79% peut apparaître sur /bibliographie avec son analyse individuelle détaillée, sans être mentionné dans la synthèse du jour — les deux seuils (75% et 80%) ne sont pas alignés dans le code actuel.
↓Entrée : articles ≥80% avec ai_analysis
↑Sortie : ai_summary (thèmes + synthèse), run completed
∞

Consultation — asynchrone, sans polling

À la demande

Contrairement à l'ancienne version de ce pipeline (bouton "Lancer la veille" + polling toutes les 2s pendant ~20s), le front ne déclenche plus rien et n'attend plus rien. La page /bibliographie est en lecture seule : elle affiche les articles ≥75% déjà scorés et analysés par le run automatique de la nuit, avec pagination, filtres lu/non-lu et pertinence.

Il n'y a plus de lien temporel direct entre la visite du chercheur et l'exécution du pipeline — les deux sont totalement découplés.

Pourquoi ce changement de modèle ?
Le pipeline dure maintenant plusieurs minutes (scoring complet, sans cap), pas ~20 secondes. Un modèle batch nocturne + consultation différée est plus adapté qu'une interaction "clic → attente → résultat" en temps réel.
↓Entrée : visite de /bibliographie, à tout moment
↑Sortie : articles déjà scorés, triés et paginés
Outils et bibliothèques — pourquoi chacun ?
Flux RSS
Format standard — fourni par les éditeurs

Format XML que chaque journal met à jour à chaque publication. C'est le moyen officiel de suivre les nouvelles publications sans avoir à scraper les sites web. 44 des 46 sources RSS actives l'utilisent (les 2 restantes sont orphelines, sans URL RSS valide). Gratuit, stable, légal.

OpenAlex
Base de données bibliographique ouverte — API gratuite

Référence 250+ millions d'articles avec leurs métadonnées complètes. Utilisé pour trois choses : combler les métadonnées manquantes des RSS, couvrir les 2 journaux sans RSS (MDPI, source_type='openalex'), et vérifier is_final (publication vs preprint). Entièrement gratuit, sans clé API requise.

CrossRef
Registre mondial des DOIs — API gratuite

Utilisé en fallback uniquement : quand OpenAlex ne confirme pas qu'un article est définitivement publié (is_final), CrossRef vérifie la présence de volume/issue dans ses propres métadonnées avant de trancher.

Semantic Scholar
API de recommandations — optionnelle

Source de veille activable (ENABLE_SEMANTIC_SCHOLAR=true) qui suggère des articles récents similaires aux publications représentatives du chercheur, au-delà des journaux explicitement surveillés.

Xenova / all-MiniLM-L6-v2
Modèle d'embedding — tourne localement sur le runner

Transforme un texte en vecteur de 384 nombres. Chaque abstract est d'abord découpé en chunks de ~150 mots avant embedding, pour un meilleur signal sémantique. Aucun appel API payant.

pgvector — match_chunks / match_author_chunks
Extension Postgres — comparaison de vecteurs en base

Deux RPC distinctes : match_chunks compare au corpus complet (en excluant les chunks temporaires d'analyses non intégrées), match_author_chunks restreint la comparaison aux seuls articles du chercheur. Index IVFFlat, pas HNSW (voir docs/DECISIONS.md D12).

GPT-4o-mini (fetch natif)
Génération — analyse individuelle + synthèse globale

Appelé via fetch natif, jamais via le SDK openai officiel — le SDK utilise undici en interne, incompatible avec les contextes background de longue durée. Deux appels distincts : un par article (Job 3, top 8) et un pour la synthèse globale (Job 4, seuil 80%).

GitHub Actions
Orchestrateur — 4 jobs séquentiels + 1 optionnel parallèle

Remplace Vercel comme runtime d'exécution de la veille. Chaque job est un script Node.js indépendant ; le run_id passe de l'un à l'autre via les outputs GitHub Actions. Pas de limite de durée serverless comme sur Vercel.
